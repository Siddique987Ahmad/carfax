# db/08 — Seed data for development and demos

Status: done (Nov 27, 2026) · Phase: pre-pilot · Depends on: db/02 to db/07

## Goal
One command fills a local or staging database with realistic data, so developers can build screens and the team can demo the product before real garages use it.

## Decisions
- **Two seed sets:**
  - `dev`: a lot of varied data for building and testing.
  - `demo`: a small, polished set for showing to garage owners and dealers.
- **Same data every time,** using a fixed random seed, so bugs can be reproduced.
- **Includes the edge cases the app must handle:**
  - Mileage drops (rollbacks)
  - Jobs with no photo
  - A misread odometer
  - Two copies of the same car
  - Suspended and pending garages
- **Can never run against production.** The command refuses if `NODE_ENV` or the database name says production.
- **Photos point at a few sample images** uploaded to local storage, not real customer photos.
- **Built with these changes:**
  - **No faker.** It doesn't know Pakistani car models, plate series or local chassis formats, so the data is curated (`seed/data.ts`: Mehran, Alto, Corolla, City, imported Aqua/Vitz/Vezel with real frame-number prefixes, Lahore `LE*` plates, Nicholson Road and Montgomery Road garages) with a small seeded generator (`seed/rng.ts`). **Ids are generated by the same generator,** so they're identical every run too.
  - **Dates are relative to today,** so due reminders and recent jobs always look current. The content and ids are the same on any given day.
  - **More edge cases than planned:** a plate that moved to another car (db/04b), broken odometers (no flag), too many visits in a week, a suspended garage whose recent jobs lack photos, car aliases, audit entries for approvals, and a resolved rollback flag with an ops note in the demo.
  - **Reminders count as "came back" only when the car returns after the reminder went out and within 30 days of the due date** (about a third), so the dashboard's success rate (admin/16) is meaningful. The first version counted earlier visits too and showed 100%.
  - **`pnpm db:reset:demo`** added, since `db:reset` always loads the dev data. `db:seed` refuses a database that already has data.
  - **Seeds run as the table owner** (`MIGRATION_DATABASE_URL`), so row-level security doesn't hide the rows they insert.
  - **Photo files aren't uploaded yet.** Rows point at storage keys under `seed/`. Uploading sample images belongs with the photo viewer (admin/10), when there's a screen to check them on.

## Scope
**In:**
- `dev` seed:
  - Platform users: 1 super admin, 1 ops, 1 support
  - 8 garages in two cities (mixed statuses), each with an owner and mechanics
  - 300 cars, 2,000 jobs over 18 months, about 5% flagged
  - Customers and reminders
- `demo` seed:
  - 3 garages
  - A car with a clean history
  - A car with a rollback
  - A car with accident repairs
- Commands: `db:seed`, `db:seed:demo`, `db:reset` (drop, migrate, seed; local only)

**Out (later items):**
- Report orders, payments, dealers and disputes (added to the seed when db/11 and db/12 are built)

## Steps
1. Write the seed scripts with `@faker-js/faker`, using a fixed seed and Pakistani names, cities and plate formats.
2. Build mileage series per car that rise realistically, then add the planned errors.
3. Add the production guard.
4. Add the commands and document them in `packages/db/README.md`.
